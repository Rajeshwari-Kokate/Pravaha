# PRAVAHA Interface Redesign Specification

## PART B. COLOR SYSTEM (fixed palette)
B1. Brand palette, use exactly:
pink #F6E2E9
cream #FEFAF3 (page background, light theme)
sage-300 #B8CFB3
sage-500 #84A282
Derived tokens (adjust values only as needed to pass WCAG AA, and write an automated contrast check script that tests every text and background pair in both themes):
ink #24302A (body text), ink-muted #55655B, sage-700 #4F6B52 (links, focus rings, strong accents), sage-900 #2F4A38 (headings on tinted surfaces, pressed states), water #3A7F8F (flowing water and the drainage network lines), amber #C98A1B (warnings), critical #B3261E (critical simulated conditions), white surface #FFFFFF for raised cards.
Dark theme derived from the same hues: background #1C2620, surface #25312A, border #3A4A40, text #FEFAF3, muted #B9C7BD, accent sage-300, primary sage-500, pink as a highlight tint, water #6FC0D0, amber #E6B04A, critical #F08A80.
B2. Usage:
- Page background cream, raised cards white or cream with a 1.5 px border, tinted panels use pink or sage-300 as flat fills.
- Primary buttons: sage-500 fill with ink text and a 2 px ink border. Secondary buttons: cream fill with ink border. Rectangular with an 8 px radius, never pill-shaped.
- Pink marks selection, hover fills, tags and empty states. Sage-300 marks active layers, chips and success. Sage-500 and sage-700 mark primary actions and the network UI.
- Pink and sage tints are never used for text or essential icons on light backgrounds, use ink or sage-700.
- Because pink sits near red, critical status always combines deep critical red, an icon and a text label. Never rely on color alone.
- Accumulation ramp for hotspots (sequential data scale, the only multi-color scale allowed): sage-300 (low), #E8C468 (moderate), #E0803A (high), #B3261E (very high), with a labelled legend and a hatch pattern on very high so it works without color.
- No gradients anywhere in the interface (the accumulation ramp is a discrete or data-driven scale, not decoration). No purple.
- Observed data uses solid lines, synthetic data uses dashed lines with a persistent "Synthetic" label.
B3. Define every color once as CSS variables and Tailwind theme tokens. Remove all old palette values (blush, lavender, navy) from the codebase.

## PART C. DESIGN LANGUAGE AND LAYOUTS
C1. Feel: friendly engineering software. Warm, tactile, clear. Cards have a 12 to 16 px radius and a 1.5 px border. Raised elements use a flat offset shadow (for example 3 px 3 px 0 in a darker sage or ink tint, no blur) that shrinks when pressed. Tags are rectangular with a 4 px radius. Spacing on a 4 px grid, one consistent type scale. Headings use a friendly geometric sans (self-host Bricolage Grotesque via fontsource), body uses DM Sans, IDs and numbers use JetBrains Mono. Self-host fonts through npm packages, do not load them from a CDN, and mention it in /privacy. Icons: Lucide only. No emoji. No photos. No AI-generated images.
C2. Brand: the existing custom SVG wave and drainage mark with the wordmark "PRAVAHA" and the small line "Urban Flood Intelligence". Keep the same mark in the header, report header and favicon, recolored to the new palette.
C3. Page layouts (follow the attached mockup's structure, using the new palette and light theme by default, dark theme available):
Landing (/): top nav with logo, links Home, Methodology, Workspace, Learn, plus a primary "Open Workspace" button, search icon and theme toggle. Left-aligned headline "Investigate urban flooding before the next storm." with the supporting text and two buttons ("Open flood workspace", "Explore the methodology"). The hero background or right half is the REAL interactive MapLibre map of the demonstration network, not a photo. Below it a row of three workflow items with Lucide icons: "Analyse scenarios", "Identify risk areas", "Plan informed actions", each with one factual sentence. Then methodology summary, limitations, FAQ, footer.
Workspace (/workspace): slim left sidebar with the mark and items Workspace, Scenarios, Reports, Methodology, plus Settings and Help at the bottom. Top bar with the page title "Flood Workspace", a one-line subtitle, and the demo area label (a selector only if more than one area exists, otherwise a static label naming the real study area). Center: the map. Overlay panel at the top left on the map titled "Layers" with toggles for Drainage Network, Road Network, Surface Elevation (only if real data exists), Simulated Flooding, Key Infrastructure, and a Base Map select. Right panel "Simulation Controls": rainfall intensity slider with tick labels, duration slider with tick labels, drainage capacity select, a "Run Simulation" primary button and a "Reset" secondary button. Bottom area "Simulation Results (Summary)": three KPI tiles (Potential hotspots, Drainage segments over capacity, Road segments affected) with a Low, Moderate, High legend, and tabs for the asset table, comparison, events and the timeline scrubber. Slider ranges and defaults come from real dataset column ranges where available.
Scenario Comparison (/scenarios): title "Scenario Comparison" and subtitle "Compare baseline conditions with intervention scenarios." Two side-by-side map cards, "Baseline Scenario" and "After Intervention", each showing its parameters in a subtitle line and the relative accumulation legend (Low to High). A "Comparison Metrics" card lists hotspots, over-capacity segments and affected road segments as before then after with the computed change. If a metric did not change show "no measurable change". Footnote: "Values are based on the current simulation and are relative indicators, not real-time measurements."
Segment detail (selected feature page or large drawer): a "Back to map" link, the segment title (for example "Drainage Segment D-104") with an amber "Candidate Bottleneck" tag, tabs Overview, Upstream Network, Downstream Network, Related Hotspots. Overview is a label and value table: Segment ID, Type, Length, Nominal Capacity, Current Flow (Simulated), Capacity Utilization, Connected Nodes, Status, plus Provenance with the "Synthetic" label. Beside it a mini map highlighting the selected segment, with a legend (Selected Segment, Connected Network, Over Capacity, Other Segments, Node). Below, chart tabs: Flow Profile (simulated flow versus nominal capacity along distance, computed from the graph path) and Elevation Profile (only if real elevation exists). Also show the ranking factors and weights behind the candidate bottleneck score.
Report (/reports/:id): header with the mark, "Investigation Report", a subtitle saying the narrative is generated by Gemma 4 from simulated data, and buttons "Download PDF" (implemented as a print-friendly layout opened through the print dialog, labelled "Print or save as PDF" in a tooltip) and "Export JSON". Left section navigation: Executive Summary, Key Findings, Affected Infrastructure, Bottleneck Analysis, Scenario Comparison, Suggested Inspection Priorities, Methodology and Assumptions. Executive Summary and Key Findings come from the validated Gemma output with evidence ID chips, or an honest unavailable state.
Methodology (/methodology): left sub-navigation Data Sources, Simulation Approach, Drainage Network Model, Bottleneck Analysis, Dataset and Model Card, Limitations, Future Work. The Data Sources section is a table with columns Dataset, Source, Description, Licence built ONLY from the real sources and licences recorded in docs/DATA_PROVENANCE.md and docs/DATASET_REPORT.md. Do not copy any dataset names, licences or numbers from the mockup, they are placeholders.
All other pages (Learn, Contact, Privacy, Terms, 404) adopt the same shell, tokens and components.
C4. Responsive: on tablet and phone the sidebar becomes a menu, the workspace panels become tabs or bottom drawers, comparison cards stack, tables scroll inside their own container.

## PART D. PLAYFUL, USEFUL INTERACTIONS (every one must do real work, be fast, and respect prefers-reduced-motion)
D1. Flowing pipes: drainage lines animate with moving dashes whose speed reflects relative simulated flow, and the line color shifts to the warning and critical styles when utilization passes 100 percent. Paused when the simulation is paused. Static under reduced motion.
D2. Rain on the map: while a simulation plays, a light overlay of thin raindrop streaks falls over the map, with density tied to rainfall intensity. A "Rain effect" toggle in Settings, default on while running, off under reduced motion. Keep it subtle and capped for performance.
D3. Water gauge: the segment detail shows a small cross-section of a pipe that fills to its simulated capacity utilization, with a gentle ripple and an overflow state above 100 percent plus the numeric value and label.
D4. Storm presets: friendly chips above the controls that set real parameters, for example "Light rain", "Heavy storm", "Cloudburst". Each chip shows its mm/hr and duration, and a tooltip says it is a design storm for exploration, not a forecast. Values come from dataset ranges or documented design-storm references.
D5. Tactile controls: chunky slider thumbs, springy toggles, pressed button states, lift and offset shadow on card hover, pulse on the hovered map segment. Animations 150 to 250 ms, no bounce on layout, no animated counters.
D6. Friendly empty and loading states: small original line SVGs (a drain grate, a pipe, a raindrop) with useful text such as "No simulation yet. Pick a storm, press Run, then see which pipes can't keep up." Skeleton loaders in the palette. These are functional states, not decoration.
D7. First-visit guided tour: five short steps highlighting the layers panel, controls, run button, results and comparison. Skippable, keyboard accessible, remembered in localStorage as an essential item, restartable from Help.
D8. Honest celebration: when a scenario comparison shows a real measurable reduction, show a small "Fewer hotspots than baseline" stamp with the computed numbers. Nothing when there is no change, and show the no-change message instead.
D9. Flood school: lesson completion shown as rectangular stamps, progress in localStorage only, no leaderboards or fake social features.
D10. Microcopy: warm, plain, specific, short. No em dashes, no hype, no AI-sounding phrases, no claims of accuracy or prevention.

## PART E. REMOVALS AND LIMITS
E1. Remove the custom cursor completely: delete the component, its CSS and listeners, and any related tests and docs. Use only native cursors everywhere (pointer on interactive elements, grab and grabbing on the map). Remove the cursor rule from docs/SPEC.md.
E2. Keep these existing rules: no pill buttons, no emoji, no AI-generated images, no fake metrics, counters or reviews, no scroll-triggered effects beyond the thin progress bar, no "Made with AI" badges, no em dashes, no operational warning claims, simulated and synthetic data always labelled.
E3. Do not add routes that are not in the spec. Do not change engine formulas, API shapes or test expectations unless a test is genuinely wrong, and log any such change.
